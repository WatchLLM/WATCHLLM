# WatchLLM Schemas Audit Specification (JSON Schemas)

This document defines the expected perfect state of the **WatchLLM Schemas** repository. It outlines the architecture, rules, interface contracts, and edge cases necessary to pass a complete verification run.

---

## 1. Purpose & Scope
The Schemas repository acts as the central interface registry for the WatchLLM ecosystem. It defines the machine-level JSON contracts (Draft-07 JSON Schema) used to communicate data between the Kernel, Rust Runtime, VS Code Extension, Klyd Memory, and the Replay server, preventing communication divergence across different languages (Python, Rust, TypeScript).

---

## 2. Expected Directory & File Layout
A perfect implementation must contain:

## 3. Core Schema Contract Definitions

### A. Violation Schema (`violation.json`)
- Describes an individual rule transgression.
- **Fields**:
  - `rule_id`: String (Required).
  - `message`: String (Required).
  - `line`: Integer, minimum 1 (Optional).
  - `column`: Integer, minimum 0 (Optional).
  - `code_context`: String (Optional).
  - `evidence`: String (Optional).
- **Edge cases**: Location metrics (`line`, `column`, `code_context`) can be represented as `null` or empty when the parser is unable to pin down coordinates.

### B. Decision Schema (`decision.json`)
- Represents the results generated by the core evaluation engine.
- **Fields**:
  - `decision`: String enum (`"ALLOW"`, `"BLOCK"`, `"INCONCLUSIVE"`).
  - `mode`: String enum (`"enforce"`, `"shadow"`).
  - `file_path`: String (Required).
  - `rule_results`: Array of rule outcomes containing `rule_id`, `status` (`PASS`/`FAIL`), and `violations` list.

### C. Kernel Execution Result Schema (`kernel_execution_result.json`)
- The structural interface contract consumed by the VS Code extension diagnostics mapper.
- **Fields**:
  - `status`: String enum (`"success"`, `"failed"`, `"error"`).
  - `exit_code`: Integer enum (`0`, `1`, `2`).
  - `payload`: Object containing `allowed` (boolean) and a flat `violations` array.

## 4. Cross-Language & Versioning Invariants

### 4.1 Draft-07 JSON Schema Compliance
- All schemas must compile against standard Draft-07 specifications without using language-specific syntax extensions. This ensures parity when parsed by Python's `jsonschema` library and Rust's `jsonschema` crate.

### 4.2 Semantic Versioning
- Breaking changes (removing fields, adding required fields) are forbidden within the `v1/` directory. If a contract changes incompatibly, a new version folder (e.g. `v2/`) must be created.

---

## 5. Critical Edge Cases & Error Recovery

| Edge Case | Expected Perfect Behavior |
|---|---|
| **Python `None` vs JSON `null`** | Dataclass fields in Python evaluate to `None` when empty. The JSON representation translates to `null`. The schema must declare nullable fields utilizing `oneOf: [{"type": "null"}, {"type": "object"}]` mappings. |
| **Additional Properties** | Third-party extensions can append metadata to telemetry/violation reports. The schemas should set `additionalProperties: true` (or leave it unchecked) for warnings/telemetry to avoid schema check failure, but restrict critical fields. |
| **Severity Mismatch** | Python rules define enums (`CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `INFO`), whereas Rust core logs strings (`error`, `warning`). The severity field in `violation.json` must permit both formats using a regex or enum union. |

## 6. Verification Checklist
To confirm Schemas compliance, run:
1. **Schema Validation**: Verify that the JSON files compile and pass validation:
   ```python
   import json
   from jsonschema import Draft7Validator
   with open('schemas/v1/decision.json') as f:
       Draft7Validator.check_schema(json.load(f))
   ```
2. **Payload Integration**: Validate mock outputs from the Python kernel and Rust runtime against `decision.json` and `kernel_execution_result.json` respectively.
