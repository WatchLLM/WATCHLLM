# WebProof Edge (private)

Closed-source Cloudflare Worker that ingests commitments and, only when explicitly enabled, anchors them. Current Rust output is `local_merkle_stub`, `attestation=false`; it is not remotely verified. Only `verification_mode=commitment_only` is accepted. Metadata is validated but not claimed to be bound by the supplied leaf hash.

## API and storage flow

`POST /proof` (Bearer `key_id.secret`) validates the strict envelope v1 carrying Rust proof version `1.0.0`, Rust-domain Merkle path, and ≤1 MiB decoded canonical base64 payload. It reserves the unique root in D1 and writes bytes to R2. With `ANCHORING_MODE=enabled`, it then queues only a small pointer and reports `queued`. With `ANCHORING_MODE=disabled`, it reports the explicit nonterminal `stored` state and `anchoring_mode: disabled`; it does not send a Queue message. Success is `202` with nullable L2 transaction hash and commitment-only, non-attested semantics. Same-root immutable conflicts return `409`. `GET /proof/:verification_id` reports `stored | queued | processing | submitted | anchored | failed`.

Hashes accept prefixed/unprefixed 32-byte hex and canonicalize lowercase `0x`. Path direction follows leaf-index bits and historical node domain `watchllm-webproof-local-node-v1\0`. A sibling path cannot independently establish odd-level duplication context. The public Python SDK's explicit `build_edge_envelope` bridge derives this path from native canonical records and uploads a canonical payload containing the native proof plus record snapshots. `test/fixtures/python-envelope-v1.json` is generated by an installed native Python wheel and is accepted by the Worker validator in the cross-boundary test.

D1 is authoritative. R2/Queue failures mark a retryable failed reservation; queue failure also removes the object where safe. Duplicate POST repairs failed ingestion. In enabled mode no `202` precedes queue handoff; in disabled mode no `202 stored` precedes both R2 persistence and the D1 transition to `stored`. D1 fixed UTC-minute atomic conditional UPSERT allows exactly 100 accepted validation attempts/key, then returns 429 headers. No KV or isolate counter.

## Explicit staging mode

`ANCHORING_MODE` is required and accepts exactly `enabled` or `disabled`; absence, case variants, and aliases fail closed. The checked-in Wrangler configuration is deliberately `disabled` for unfunded-wallet staging. In this mode ingestion validates/authenticates/rate-limits normally and durably stores D1 metadata plus the R2 payload, but it does **not** enqueue, acquire an anchor lease, increment attempts, call RPC, or sign. The Queue consumer also acknowledges any residual delivery immediately before DB/RPC/signing access, preventing retries from being consumed after a mode switch. `stored` does not mean queued, submitted, anchored, verified, or attested. Stored rows are not automatically promoted when the mode later changes; intentional backfill/requeue requires a separate reviewed operation.

## Chain and retries

Base Sepolia (`84532`) defaults; Base mainnet (`8453`) is explicit. The viem adapter estimates EIP-1559 gas/fees immediately before signing real `anchor(bytes32)` calldata. Missing/placeholder contract, key, or chain mismatch fails closed. Execution-fee ceilings defer with Queue exponential backoff+jitter. Signed hash+nonce persist before raw broadcast; uncertain broadcasts are reconciled, never blindly replaced. Configured confirmations are required for `anchored`. RPC fallback never switches chains. Single-root transactions are v1; production economics require epoch super-root batching.

## Setup (instructions only)

Create D1, R2, producer Queue and DLQ; replace all `wrangler.toml` placeholders. New databases use `schema.sql`. Existing pre-mode databases must apply `migrations/0002_anchoring_mode.sql` before deploying this code; it rebuilds the constrained table and labels all historical rows `anchoring_mode=enabled`. Then set:

```sh
npx wrangler secret put API_KEY_PEPPER
# Required only before switching ANCHORING_MODE to enabled:
npx wrangler secret put EVM_PRIVATE_KEY
```

Provision `key_id.secret` offline: random 16-byte lowercase-hex salt, with D1 digest BLOB `HMAC-SHA256(API_KEY_PEPPER, salt + NUL + secret)`. Never store/log tokens. A separately reviewed deployed anchor contract is required; no address is invented here.

Run `npm ci && npm test && npm run typecheck && npm run lint && npm run check:schema && npm run dry-run && npm audit --audit-level=high`. Actual deployment/resources/transactions require explicit approval. Broad production also requires a real verifier, batching, and signer KMS/HSM hardening.

The fee ceiling is execution-only (`gas × maxFeePerGas`); Base L1 data fee is not exposed by the pre-signing estimator and is therefore not claimed as covered. RPC fallback has zero retries and transaction broadcast is invoked once; uncertain broadcast is reconciled by persisted hash.

Every batch is owned by the authenticated `key_id`; status lookup requires that same owner. A root is globally unique, and cross-owner duplicate submission returns a generic conflict without cached-state disclosure. Anchor consumers use an atomic expiring D1 lease; only the lease holder may persist a signed hash, and broadcast is forbidden unless that conditional persistence changes exactly one row. A stale lease is reclaimable, while any persisted transaction is receipt-reconciled rather than replaced.

SDK submission is deliberately opt-in and uses `Authorization: Bearer key_id.secret` for both POST and GET. The SDK requires HTTPS, refuses URL credentials/query/fragment, disables redirects, and sanitizes transport/HTTP failures rather than including tokens or remote response bodies in exceptions. Native local records do not commit to response bytes or observation time, so envelope `leaf_data.response_hash` and `timestamp` remain explicitly caller-supplied, `metadata_bound=0` compatibility metadata; ingestion must not present them as proven by the leaf.

The D1 `batch()` reservation writes the batch and leaf together atomically. Queue send success followed by a D1 status-write failure is still a durable handoff: the response reports queued and the consumer can claim the processing row. Queue-send failure removes the R2 object when possible; if deletion itself fails, bucket lifecycle/orphan reconciliation by digest is the documented cleanup boundary.
